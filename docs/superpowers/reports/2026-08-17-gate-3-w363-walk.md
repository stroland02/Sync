## Why this walk exists, and the treadmill it settles

The previous signature was `2026-08-17T13:28:32-04:00`. The console changed at 14:36, then 15:32,
then 16:40 — three landings, each of which reset the timestamp the signature has to be newer than.
`scripts/beta_gates.py:322` reads `console_changed_at > latest` and returns `CANNOT TELL`, so the
gate was never green for more than the gap between two units of work.

**That is the gate working, not failing.** A console that changes every hour cannot carry a
standing claim that a walk done before those changes still describes it. What was wrong was the
expectation that Gate 3 could stay green during active development, and the response of re-signing
faster. You cannot sign a console you are still changing.

So `web/src` was frozen at `4a5ef47` before this walk began, and stays frozen until this signature
is on `main`. The ordering — freeze, walk, sign, land, then unfreeze — is what makes the signature
mean anything.

## Method

API on 8799, console on 4199, both stopped afterwards and confirmed dead by asking the socket.
`dist/` was rebuilt from `4a5ef47` before the walk: the bundle predated the merge of 31 commits
from `origin/main`, and walking a stale bundle would have signed a console that is not the one on
disk. Subjects were read off the running API rather than hardcoded, so a reseed cannot quietly fill
the walk with not-found screens.

Credentials travelled as a header. Chrome does not attach URL-embedded credentials to a page's own
`fetch` calls, so a walk done that way reads a console whose every panel failed — the mistake that
invalidated three earlier measurements in this work.

The Chrome viewport override was cleared afterwards.

## Verdict: PASS, with two findings, one of them new

Seven of nine screens are clean. The two findings below are recorded rather than fixed, because

### Finding 1 — `CONTEXT SAVINGS` is still a model rendered as a measurement (B145, known)

Three screens show it: Codebase (`1,600 tokens`), the API service (`1,600 tokens`), and the finding
(`800 tokens`). `types.ts:110` says plainly what it is — `total_findings * a constant`. The figure
is rendered flat, with no qualification, unless `context_savings_bound_reached` is set, in which
case `provenance.tsx:99-105` adds the honest floor sentence.

**This does not block the signature, on established precedent.** The 11:10 walk traced this exact
figure to its computation, named the modelling gap, filed it as **B145**, and recorded
`Verdict: PASS` with the gap named (`2026-08-17-gate-3-screen-pass.md:119-133`). The values have
moved (1,200/400 then, 1,600/1,600/800 now) only because the seed changed. Nothing about the claim
has changed, so nothing about the verdict does either.

### Finding 2 — NEW: two screens say the API does not hold a repository the API demonstrably holds

Codebase and Signals each render two failed panels for
`github.com/stripe/stripe-connect-furever-demo`, and the copy above them reads:

> The API does not hold that identifier.
> not found (`/api/repositories/github.com%2Fstripe%2Fstripe-connect-furever-demo/coverage`)

**That sentence is false.** `/api/repositories` lists that repository, and the repository's own
route renders it — the screen's header, its four open findings, its vendor table and its change
unit all resolve. Only `/coverage` and `/observed` 404.

The cause is the one the IA survey corrected B147's filing to: `app.py:422-423` declare those two
routes with `{repo_id}`, Starlette's default path converter, which does not match a value
containing `/`. The routes at `:426-429` already use `{repo_id:path}` and carry a comment saying
why. Every repository whose id is a `host/owner/name` triple therefore 404s on exactly those two
panels — which is why this was invisible while the seed held only `seed-console-repo-a` style ids.

Two separate defects sit here and they belong to different lanes:

- **The routing bug is B147** (Lane E), and this walk is a clean reproduction of it with the
  corrected cause confirmed rather than inferred.
- **The copy is a console defect and it is mine.** A 404 means a route did not resolve. It does not
  license the claim that the API does not hold the identifier — the console cannot know that from a
  status code, and here it is wrong. This needs its own backlog number, which I do not have: my
  block (B146–B149) is exhausted and I will not invent one after telling the coordinator that
  inventing numbers was the IA plan's defect. **Filed as a request to the coordinator, unnumbered,
  in the same message that reports this walk.**

**Why this still passes.** Gate 3 asks whether a screen asserts a figure nothing computed. This
asserts no figure; the failed panels compute nothing and claim nothing numeric, and the exact
failing URL is printed beside the sentence, so the evidence contradicting the claim is on screen
next to it. It is a wording defect in an error path, not a fabricated measurement — and it is
recorded here rather than waved through.
