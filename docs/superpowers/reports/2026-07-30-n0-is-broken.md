# A serial run sweeps away its own database

**Date:** 2026-07-30
**Scope:** M3-W105 — diagnose the 186 errors M3-W102 found under `-n0` and declined to explain.
**Outcome:** one cause, 186 instances. Two tests in `tests/test_leaked_database_sweep.py` tell the
sweep that every database named for this process is dead, and under `-n0` the run's own database is
one of those. `-n0` is contracted to work in four places, so it is fixed rather than documented
away. `pytest_configure` is untouched.

## 1. Reproduction

W102's pinned recipe, re-run verbatim on `origin/main` at `8187a9b`:

    uv run pytest -q -n0 tests/test_leaked_database_sweep.py tests/test_migration_corpus.py

**No `--cov` at all** — this defect is not a coverage defect, and the `--cov` form is reported
throughout this document because a dotted `--cov=<module>` changes program behaviour in this
repository (`2026-07-29-psycopg-error-identity.md`) and two committed corrections came from
comparing across forms.

| | |
|---|---|
| result | **32 passed, 4 errors** |
| exit code | **1** |
| wall clock | **33.04 s** |
| `--cov` form | **none passed** |

W102 measured `32 passed, 4 errors` in 32.35 s. Reproduced within noise.

Every one of the four errors is the same string, and the database named is the run's own:

    FATAL:  database "sync_test_15584" does not exist

## 2. One cause, 186 instances

The grouping is total, on three axes at once.

| axis | grouping |
|---|---|
| error type | `psycopg.OperationalError`, 4 of 4 |
| message | `database "sync_test_15584" does not exist`, 4 of 4 — one distinct database name |
| phase | setup, 4 of 4; no test body runs |

There is nothing to subdivide: one database disappears, and every later test that needs Postgres
fails to connect to it. In the full-suite run W102 recorded, that is 186 tests rather than 4. The
count is a function of how many Postgres-touching tests are scheduled after the drop, not of how
many things are wrong.

**Bisected, not inferred.** Deselecting two tests by name — and changing nothing else — makes the
same recipe green:

    uv run pytest -q -n0 tests/test_leaked_database_sweep.py tests/test_migration_corpus.py \
      --deselect tests/test_leaked_database_sweep.py::test_a_database_in_use_is_refused_rather_than_force_dropped \
      --deselect tests/test_leaked_database_sweep.py::test_a_database_that_cannot_be_dropped_does_not_fail_the_run

**34 passed, 2 deselected, exit 0, 107.71 s.** No `--cov`. The run takes three times as long
precisely because the 4 tests that used to error now run.

## 3. What is xdist-dependent: the second pid in the database's name

Not the worker id itself, and not `conftest.py`'s naming — the naming is correct on both
schedulers. What xdist supplies is an **extra pid in the name that is not this process's**, and two
tests depend on that without saying so.

Both tests build their fixture databases as `sync_test_{os.getpid()}_gw1`, then hand the sweep a
predicate that declares this process, and only this process, dead:

```python
dead_to_the_sweep = lambda pid: pid != os.getpid()
dropped = sweep_leaked_databases(ADMIN, is_running=dead_to_the_sweep)
```

That is deliberate and it is documented in both docstrings: naming the fixtures for a genuinely
dead pid lets a concurrent suite drop them, so they are named for a live pid and lied about
instead. The lie is over-broad. It reaches every candidate whose name carries no pid except this
one — and under `-n0` the run's own database is exactly that.

`leaked_database_names` spares a name when **any** pid in it is running. So:

| scheduler | the run's own database | pids in it | `dead_to_the_sweep` says | outcome |
|---|---|---|---|---|
| `-n0` | `sync_test_16848` | `[16848]` — this process | all dead | **swept** |
| `-n auto` | `sync_test_99999_gw0_p16848` | `[99999, 16848]` — controller, then worker | 99999 alive | spared |

**Measured directly, no pytest and no coverage, in 2 s.** Names built by `conftest.database_for`
rather than written out, both databases really created on the server, and the real
`sweep_leaked_databases` called:

    serial-run own database  : sync_test_16848
    worker-run own database  : sync_test_99999_gw0_p16848
    decision, serial shape   : ['sync_test_16848']
    decision, worker shape   : []
    sweep dropped serial     : True
    sweep dropped worker     : False

So the run's own database survives `-n auto` **by accident**, and by the accident of the very
predicate written to call everything dead: under xdist the controller's pid is "not me", so the
predicate reports it alive and the name is spared. Under `-n0` there is no controller pid to be
saved by. `tests/conftest.py:73` already records that the leading pid belongs to the process that
*generated* the name rather than the one using it; this is the same fact reached from the other
side.

**Why W102's `exclude` experiment did not settle it, and why it was not wrong.** Threading
`exclude=<the run's own database>` through those two call sites is the correct fix and it is what
this task applies. W102 reported that it did not fix the run, and that report was taken under the
full-suite dotted `--cov=sync.benchmark.mutate` configuration rather than under the 33 s recipe.
It is not compared against here, for the reason its own report gives.

## 4. `-n0` is contracted to work, in four places

This is the question that decides whether the fix is code or documentation. It is code.

| where | what it says |
|---|---|
| `pyproject.toml:79` | "Spinning up workers costs about 4s flat, so **use `-n0` for a focused run**." |
| `docs/superpowers/specs/2026-07-29-sync-verification-regime.md:87` | "Run it with `-n0`, because `addopts` carries `-n auto` and that applies to the e2e test too." |
| `docs/superpowers/BACKLOG.md:58` | "**Run it with `-n0`.** `addopts` now carries `-n auto`, which applies to the e2e test too." |
| `docs/superpowers/reports/b5-test-suite-parallelism.md:192` | "**Run it as `uv run pytest -n0 -m e2e ...`.**" |

The middle two are the load-bearing ones. `addopts = "-m 'not e2e' -n auto"` deselects the e2e test
*and* pins the scheduler, so running the one e2e test at all means overriding `addopts`, and the
spec that governs the verification regime tells you to override it with `-n0`. `-n0` is therefore
not a debugging convenience in this repository — it is the documented way to run one specific test,
named in a binding spec.

One thing that muddies the picture and is worth stating so nobody re-derives it: the `b5` recipe
exports `SYNC_DSN` before running `-n0`, and a pinned `SYNC_DSN` dodges this defect entirely.
`database_for` returns `None` for a pinned serial run, so no per-run database is created and there
is nothing for the sweep to take. That is why the contract could hold in one place while being
broken in another.

## 5. What changed

Two call sites in `tests/test_leaked_database_sweep.py` gain one keyword argument:

```python
dropped = sweep_leaked_databases(ADMIN, is_running=dead_to_the_sweep, exclude=OWN_DATABASE)
```

`exclude` already exists and `pytest_configure` already passes it. `leaked_database_names`'s own
docstring says the guard lives in the callee "so anything reusing this function inherits it" — and
these two callers were the ones reusing it without the guard. Nothing in `sync/` changed, nothing
in `tests/conftest.py` changed, and **`pytest_configure` is untouched**: no statement in that hook
was read, moved or edited, so the failure mode where an exception escaping it kills a session
before collection is not in play.

`addopts` is unchanged and should be. `-n auto` is the right default — it is 133 s to 46 s on this
machine — and the defect was never in the scheduler. Widening `addopts` to make `-n0` the default,
or narrowing it so `-n0` is unreachable, would both be treating the symptom.

Two new tests:

- **`test_the_run_s_own_database_survives_every_sweep_in_this_file`**, last in the sweep file. It
  reports on what ran before it, so its position is load-bearing and the docstring says so. It
  cannot fail under `-n auto`, which is the whole reason the defect survived.
- **`tests/test_serial_run_isolation.py`**, a new file. It runs the two sweeps and the canary in a
  child process under `-n0`, from a parent running whatever `addopts` says, and asserts the child
  exits 0 having run three tests. This is the only thing in the suite that can see the serial
  configuration at all.

The child's environment has `SYNC_DSN`, `PYTEST_XDIST_WORKER`, `PYTEST_XDIST_TESTRUNUID` and
`PYTEST_CURRENT_TEST` removed, so it creates and owns a database rather than borrowing the
parent's. Node ids rather than a `-k` expression: a rename makes pytest exit 4 on a collection
error, which the exit-code assertion reads as a failure, where a `-k` expression that stopped
matching would exit 5 having quietly run nothing.

## 6. Mutations

Harness at `.cache/w105/mutate.py` (gitignored). It `compile()`s every mutant before writing,
refuses an anchor that does not match exactly once, passes `--color=no` and `PYTHONIOENCODING=utf-8`
to every child, reads children with `errors="replace"`, restores from the **original bytes** rather
than from normalised text — these files are CRLF and `write_text` would have left a diff the
harness invented — and runs pytest unpiped, reading its own exit code rather than a pipeline's.

**Four outcomes, not two.** `KILLED` requires exit 1 *and* a `1 failed` line; `SURVIVED` requires
exit 0 *and* a `1 passed` line and no `1 failed`; everything else is `UNREADABLE` and prints the
exit code. This is not defensive decoration: `pytest -p no:xdist` against this repo's `addopts`
exits **4** with zero `FAILED` lines, and a two-outcome harness reads that as a clean run.
`DID-NOT-COMPILE` is a separate branch taken before anything is written, and `BASELINE-DRIFTED` is
checked by re-running the gate after every mutant is restored.

Baseline `1 passed in 16.59 s`; restored baseline green with the same count, so nothing drifted.

| mutation | verdict | note |
|---|---|---|
| `M-exclude-first` — `exclude` removed from the first sweep only | **KILLED**, `1 failed in 17.27s` | either site alone loses the database |
| `M-exclude-second` — `exclude` removed from the second sweep only | **KILLED**, `1 failed in 17.24s` | so the fix is needed twice, not once |
| `M-both` — both removed, i.e. the tree as it was | **KILLED**, `1 failed in 17.19s` | the change under test |
| `M-canary-blind` — both removed *and* the canary asserts on `postgres` instead | **SURVIVED**, `1 passed in 84.52s` | the diagnostic: it is the canary's assertion that kills the three above, not an incidental effect |
| `M-canary-skipped` — both removed *and* the canary marked `skip` | **KILLED**, `1 failed in 18.01s` | exit 0 from the child; only `"3 passed" in stdout` catches it |
| `M-stale-node-id` — one node id renamed to something absent | **KILLED**, `1 failed in 6.21s` | pytest exits 4; the exit-code assertion covers node-id drift |

`M-canary-blind` is the honesty check, the same role `M-split-guard` played in
`2026-07-29-psycopg-error-identity.md`. A test can pass because it asserts the right thing or
because something unrelated to the assertion changed; blinding the assertion while leaving the
defect in place separates those, and its survival is the evidence that the canary is what is doing
the work.

`M-canary-skipped` is what stops the count assertion being written off as redundant. Its child
exits **0** — `2 passed, 1 skipped` — so the exit-code assertion is satisfied and only the count
catches it. That is the "did not run" false verdict, and it is the mode a suite is likeliest to
drift into silently.

Its 84.52 s against a 17 s neighbour is an outlier on a shared server rather than a signal; the
verdict, not the wall clock, is what that row establishes.

## 7. What this evidence does not cover

This is the **third** distinct account this project has had of `tests/test_leaked_database_sweep.py`
and the first two did not survive measurement, each costing a committed report a correction. So the
boundary of the evidence is drawn explicitly rather than left to be inferred.

**What is measured, and is the whole of the load-bearing claim:**

- W102's pinned recipe reproduces at **32 passed, 4 errors, exit 1, 33.04 s**, `--cov` **absent**.
- Deselecting two named tests and changing nothing else makes that same command **exit 0**.
- Calling the real `sweep_leaked_databases` with the real predicate against two real databases
  built by `conftest.database_for` drops the serial-shaped name and spares the worker-shaped one.
- Removing `exclude` from **either** call site alone turns the pinned test red; the tree with both
  present is green.

**What is not measured, and should not be read into the above:**

- **The number 186 is W102's, not re-taken here.** What is re-taken is the 4-error two-file recipe.
  The claim that the same cause produces 186 in a full suite rests on the errors being identical in
  type, message and phase and on the fix turning the full `-n0` gate green — not on a second count
  under W102's configuration.
- **The dotted `--cov=sync.benchmark.mutate` configuration is not re-run at all.** W102's 186 was
  taken under it. Every measurement in this report has **no `--cov`**, and none of them is compared
  against one that has. That is deliberate: a dotted `--cov` changes program behaviour in this
  repository, and comparing across the two forms is what produced the corrections.
- **"Over-broad", not "wrong".** The predicate is a deliberate device and both docstrings already
  argue for it: naming a fixture database for a genuinely dead pid gets it dropped by any
  concurrent suite. The finding is that it reaches one name more than it should. Nothing here says
  the device should go.
- **This does not establish that `-n0` has only one defect.** It establishes that this one is fixed
  and pinned. The full `-n0` gate below is the only evidence about the rest of the suite, and it
  speaks only for the tests that exist today.
- **The canary depends on collection order.** It is last in its file and pytest runs tests in
  definition order; `pytest-randomly` is not installed here — checked. Adding a randomiser would
  silently void it, and the driver test would keep passing.
- **`OWN_DATABASE` is resolved once, at module import.** That is after `pytest_configure` has set
  `SYNC_DSN`, which is the only writer today. Anything that re-points `SYNC_DSN` mid-session would
  leave it stale.
- **The ordering of the two call sites was not traced.** It did not need to be: both mutants kill
  independently, so either one alone loses the database.

## 8. For the next task, not this one

`.github/workflows/ci.yml` is out of scope here and changing what CI runs is not a drive-by. Two
things follow from this finding and belong in a task of their own:

- **The coverage step's `|| true` is one of the two things that hid this.** Its own comment says
  the not-gating is deliberate, and that is defensible on its own terms — but it means an
  ungated step is the only place a serial-ish configuration was ever exercised.
- **Nothing in CI runs `-n0`.** The configuration is contracted in a binding spec and in
  `pyproject.toml`, and no gate covers it. `tests/test_serial_run_isolation.py` now covers three
  tests' worth of it from inside the ordinary suite, which is a floor and not a substitute for a
  job that runs the suite serially.
