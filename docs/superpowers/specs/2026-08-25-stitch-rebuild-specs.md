## The frame spec

**Composition.**

TARGET GEOMETRY (1440x900 reference, dark-only, desktop-first).

The document stops scrolling. `SidebarProvider` becomes exactly `h-svh` with `overflow-hidden`, and every band below it is either fixed-height chrome or a `min-h-0 flex-1` region. Nothing computes a height by subtracting a guess at the chassis — the flex chain does it, which is why no new size token is needed.

Horizontal: sidebar reserve (240px pinned / 48px rail, unchanged, `SIDEBAR_WIDTH`) | content column `flex-1 min-w-0`. The sidebar is a sibling of the content column, never inside it (`app-frame.test.tsx` pins this and it must not move).

Content column, top to bottom, all inside `h-full overflow-hidden`:
1. `ErrorSurface` — `shrink-0`, above the banner (displaces, never floats). Height 0 when there is nothing to report.
2. `header[role=banner]` — `h-12` (48px), `shrink-0`. `sticky top-0` is DELETED: nothing scrolls under it any more, so stickiness is a lie about the mechanism. `z-30` stays.
3. `TopbarStatsSlot` — `h-12` (48px), `shrink-0`, `empty:hidden`. Unchanged. This is the second of the two 48px bars.
4. `main[data-scrollport]` — `min-h-0 flex-1`, and THE ONE SCROLL REGION for a non-locked screen: `overflow-auto`, flipped to `overflow-hidden` by `has-[[data-screen=locked]]:overflow-hidden` when the routed screen opts in. Keeps `tabIndex={-1}` and `ref={contentRef}`.
5. `footer` — `shrink-0`, pinned to the viewport bottom. Holds the status portal target (`div ref={footerRef}`) then `ChassisQualifications`. `mt-auto` is deleted — `main`'s `flex-1` is what pushes it down now, and `mt-auto` claiming to do it is a second answer to one question.

So the scrollport is `100svh - 96px (two bars) - ErrorSurface - footer`. At 1440x900 with no error: 900 - 96 - (footer, measured in Chrome, ~140px for the status band plus the two protected sentences) ≈ 664px of working height.

Inside `main`, unchanged: `div.mx-auto.max-w-[1400px] (or max-w-none when isWideRoute).p-frame.gap-8` — plus `min-h-0` added so a `flex-1` child can shrink instead of forcing the parent open. At 1440 the cap never engages, so nothing measured moves.

THREE SCREEN LAYOUTS, opted into at the `ScreenFrame` call site:
- `layout="flow"` (default, 19 screens): identical composition to today. `main` scrolls. The only visible difference is that the scrollbar belongs to `main` rather than the window, and the footer is now always on screen instead of below the fold.
- `layout="fill"` (the two canvases, replaces today's `fill` prop): content band is `flex min-h-0 flex-1 flex-col`, `main` still scrolls. Unchanged behaviour.
- `layout="locked"` (nothing yet; Findings is the first adopter next slice): content band gets `flex min-h-0 flex-1 flex-col overflow-hidden` AND stamps `data-screen="locked"`, which is what flips `main` to `overflow-hidden` through `:has()`. From there the screen owns every scrollbar on the page.

PANES. A locked screen composes `Pane` / `PaneScroll` (new, `layouts/pane.tsx`). `Pane` is `flex min-h-0 min-w-0 flex-1 flex-col overflow-hidden`; `PaneScroll` is `min-h-0 flex-1 overflow-auto`. Exactly one `PaneScroll` per pane. That pair is the whole mechanic — the `min-h-0` chain plus one `overflow-auto` — and it exists as components rather than as a paragraph because a paragraph is enforced by whoever remembers it.

Reference divergence worth stating: `repository_index_explorer/code.html` locks with `body.h-screen.overflow-hidden` plus `main.fixed.top-topbar-height.bottom-0` — one 48px bar, absolute positioning, no footer. We lock with flexbox instead of `fixed`, because our chrome is two 48px bars whose second one hides itself (`empty:hidden`) and a `fixed` top offset would be wrong on every screen that publishes no KPIs.

- `app-frame.tsx` — `--scrollport`, and a scroll reset on navigation. Add a local hook beside `AppFrame`:

```tsx
/**
 * The scrollport's height, measured and published for the sticky rails that used to guess it.
 *
 * Two rails cap themselves at `calc(100svh - 8rem)` — a guess against a chassis with one 48px bar
 * and no pinned footer. There are two bars and a pinned footer now, so the guess overshoots by
 * roughly 110px and cuts a rail's own scrollbar off below the fold. Measured rather than
 * re-guessed: one number, no chrome change can make it stale.
 */
function useScrollportVar(ref: RefObject<HTMLElement | null>) {
  useEffect(() => {
    const node = ref.current
    if (node === null || typeof ResizeObserver === "undefined") return
    const publish = () => node.style.setProperty("--scrollport", `${node.clientHeight}px`)
    publish()
    const observer = new ResizeObserver(publish)
    observer.observe(node)
    return () => observer.disconnect()
  }, [ref])
}
```

Call it as `useScrollportVar(contentRef)` in `AppFrame`. The `typeof ResizeObserver` guard follows the precedent at `features/index-graph/tree-map-d3.tsx:277`; `src/test-setup.ts:38` already stubs a no-op ResizeObserver, so jsdom never publishes and the CSS fallback stands.  * makes a locked layout push its own footer off the screen, and it is invisible until it does.

export function Pane({ children, className }: { children: ReactNode; className?: string }) {
