## The architectural spine, before any file

Slice 1 had three decisions and all three survived implementation. Two stand unchanged, one needs
a stated amendment, and this slice adds two.

### 1. One contract, two consumers — holds, with the aggregate case named

Slice 1 said the console consumes the frozen `GraphSurface` contract rather than inventing a
second one, and that a field the console needs which the surface does not expose is *a question
about the graph*. That still holds for every per-finding screen, and this slice changes nothing
about the four frozen tools.

What it did not settle is the aggregate case, and the fleet questions are all aggregate. The
surface answers "what is at risk", "what changed", "explain this call site" — questions an agent
asks about one repository it is already pointed at. It answers no question whose grain is *every
run* or *every attempt*, and adding one would be a fifth tool on a frozen surface for a consumer
that is not an agent.

**The amendment:** the transport reads per-finding answers through `GraphSurface`, and aggregate
answers through a `sync.dashboard` view model. It never issues SQL of its own and never touches
`sync.remediate`. This is the pre-flight ruling the slice-1 ledger already recorded
(`.superpowers/sdd/2026-07-30-sync-m4-dashboard/progress.md:8-13`) and then never needed, because
the shipped transport turned out stricter than the ruling allowed. The fleet is what needs it.

Mechanically this costs nothing new: `create_app` already takes `workflow_reader` as a callable
supplied by the entrypoint (`src/sync/api/app.py:70-79`, `src/sync/api/__main__.py:31-34`), so
`app.py` still constructs nothing and holds no logic. The new routes take three more callables of
the same shape.

### 2. Module boundaries mirror the domain — holds, and the fleet view is the stated exception

`features/` is named after graph entities and a directory that is not an entity is a smell. A
fleet view is not a graph entity. There is no node in the API Dependency Graph whose grain is
"every run", which is exactly why nothing answers the question today.

So `features/fleet/` is named for the question rather than for a node, and it sits *above* the
hierarchy rather than inside it: `Fleet → Codebase → API Services → Errors & Incidents → Finding →
Solution Workflow → Pull Request`. Recorded here so a future reader does not read the directory as
drift and delete it, and so nobody adds a second non-entity directory on the strength of this one.

**What became of the exception — recorded 2026-08-05.** Both halves of the sentence above failed,
and the second failed worse than the first.

The exception was granted for a *directory*. It was spent on the *root*: `/` is the fleet screen
(`web/src/lib/routes.ts:68-74`), and `Fleet` is the first member of `GRAPH_LEVELS` — the console's
own declaration of the graph's levels now opens with a level the design document never had. The
word appears zero times in
`docs/superpowers/specs/2026-07-25-sync-self-maintaining-apis-design.md`. A screen that sits above
the hierarchy and a screen that is the entry to it are different claims, and this decision only
argued the first.

"Nobody adds a second non-entity directory on the strength of this one" also failed, three times in
one day. `features/bindings/`, `features/telemetry/` and `features/detectors/` landed on 2026-08-05
(`7c69134`, `d521bde`, `d8c1f4c`), and `routes.ts` declares each of them at a graph level with a
reasoned docstring that argues placement against the other routes and never against the
specification.

The reconciliation is in `2026-08-05-sync-console-architecture.md`, Task 9. Its findings on this
decision: the fleet surface survives, because M4 is multi-tenant and a control plane holding many
repositories genuinely needs a level above one — the design document has been amended to say so.
What does not survive is the fleet surface standing in for the repository level. **The reason the
exception was easy to spend is that the level it displaced was never built**: there is no
repository selector anywhere in the console, so the root had nothing under it to be above.

**The lesson, stated so it is reusable.** A stated exception is a licence with a scope, and the
scope decays unless something checks it. This one was written down honestly, in the right file,
and read by nobody for the twenty-four hours it took three more levels to appear beside it.
`.claude/rules/console-hierarchy.md` is what now checks it.

### 3. What the console is for — holds, and it decides what the fleet view may not contain

The product position is that competitors present a black box and a result and ask for trust. That
position rules three things out of a fleet screen, and they are exactly the three a fleet screen
usually has:

- **No composite health number.** A scalar averaging three gates is the false precision the
  research already rejected twice — once for a confidence score, once for a verification level
  (`docs/superpowers/references/notes/competitor-interfaces.md:202-222`, and the run-state
  specification §6). A number that collapses "we could not check" into the same axis as "we
  checked and it passed" is the failure this console exists to replace.
- **No liveness claim.** See below.
- **No spatial canvas.** Rejected on the merits and recorded
  (`competitor-interfaces.md:182-201`).

### 4. New: liveness is not observable, so the screen reports the reading and not the verdict

There is no heartbeat, no process registry, and no run table. The only evidence a run exists is a
checkpoint row, and the only time on it is `checkpoint->>'ts'`
(`.venv/Lib/site-packages/langgraph/checkpoint/base/__init__.py:102-103`; the `checkpoints` table
carries no `created_at` — `.venv/Lib/site-packages/langgraph/checkpoint/postgres/base.py:47-56`).

That timestamp is staleness, not liveness, and the difference is load-bearing here.
`GitHubForge.await_ci` blocks *inside* the node and the graph does not yield while it waits, so a
run parked at `await_ci` writes no checkpoint for minutes by design — while a run parked at
`patch` with the same silence has probably died. One reading, two meanings, and nothing in the
data separates them.

**So the screen renders "no checkpoint for 42 minutes, at `await_ci`" with a legend that names
both readings, and never a green dot.** A dot would be a confident wrong verdict, which is the
thing this console was built to stop doing.

### 5. New: derivation happens in the view model, because that is where the test runner is

`web/package.json:6-11` defines `dev`, `build`, `lint`, `preview` and no test script. The console
has no test runner, so every claim about TypeScript logic in slice 1 was verified by
`npm run build` plus a human looking at it. That was acceptable for rendering. It is not
acceptable for classification.

Any rule with a wrong answer — which node is current, which run is terminal, how a run is grouped
— lives in Python, where `uv run pytest` can hold it and CLAUDE.md's test-first rule applies. The
console formats and renders. Adding a frontend test runner is named in *What I am not proposing*
with its cost.

## Global Constraints

- `CLAUDE.md` is binding for all Python. Test-first with a proven RED; explicit
  `encoding="utf-8"` on every `read_text`/`write_text`/`open`/`subprocess.run(text=True)`;
  comments state constraints rather than narrating edits.
- **The API stays read-only.** No route mutates the graph, triggers a run, or touches a customer
  repository. The behavioural read-only test (`tests/test_api_routes.py:313-396`) extends to every
  new route; a new route not covered by it is an untested hole in the guarantee.
- **`src/sync/mcp/tools.py` is frozen.** No new tool, no new field on an existing response, no
  widening of `whats_at_risk`. Where a screen needs something it does not hold, that is a
  question for the owner and it is asked at the bottom of this document rather than built.
- **The transport issues no SQL.** `GraphSurface` for per-finding answers, a `sync.dashboard` view
  model for aggregate ones, and `app.py` constructs neither.
- **Provenance is rendered, not dropped.** `binding_source` and `indexed_at` appear wherever a
  binding is shown, at both levels, with `bindingNullLabel` saying what null means *here*.
- **A grain sentence ships with every count.** One `migration_outcome` row is one *attempt*
  (`src/sync/graph/schema.sql:167-175`), and one checkpoint thread is one *run*, not one finding.
  A field named `findings` that holds attempts is the defect CLAUDE.md names; the payload uses
  `attempts` and `distinct_findings` as separate keys, and the screen says which is which.
- **The graph and the checkpointer are two databases.** A payload never mixes their envelopes —
  `WorkflowState` is deliberately not a `Provenance` (`web/src/api/types.ts:169-178`), and the
  run roll-up inherits that reasoning.
- **Functionality before polish.** No chart, no motion, no design system in this slice.

## What the data can and cannot answer

This section is load-bearing. Slice 1's plan named a `repositories/` feature for data no route
exposes, and the console that shipped had to write a docstring explaining why the screen does not
match its own directory name (`web/src/features/repositories/overview-page.tsx:1-8`). Every claim
below is cited; where I could not verify something, it says so.

### Answerable today, through routes that already exist

Only one thing, and it is not a fleet view: `/api/overview` returns `vendor_id`,
`open_finding_count` per vendor, and `total_findings` (`src/sync/api/app.py:81-102`). That is the
whole of the existing above-the-vendor surface. There is no run status, no outcome history, no
repository identity, and no finding age anywhere in it.

### Answerable with a `sync.dashboard` view model and a transport route — no frozen change

**Runs, across everything.** `checkpoints` is `(thread_id, checkpoint_ns, checkpoint_id,
parent_checkpoint_id, type, checkpoint JSONB, metadata)` with the primary key on the first three
(`langgraph/checkpoint/postgres/base.py:47-56`). `DISTINCT ON (thread_id)` ordered by
`checkpoint_id DESC` gives the newest checkpoint per thread; `checkpoint_id` is a UUIDv6 so text
order is creation order, which `sync.dashboard.queries` already relies on (`queries.py:192-194`).
Everything `workflow_state` computes for one finding — the pending node, the filtered outcome, the
abandon reason — is computable per thread across all of them, from the same three JSONB keys
(`queries.py:201-227`).

The thread id is `{finding_id}:{run_id or head_sha[:12]}:{generation}`
(`src/sync/cli.py:1054-1056`, and `_thread_to_invoke` at `cli.py:340-368` for the generation).
`finding_id` is a 32-character hex digest (`src/sync/graph/store.py:20-21`, written at
`store.py:375-377`), so it contains no colon and `split_part(thread_id, ':', 1)` recovers it
safely even if a caller passes a `--run-id` that does.

**Grain: one row is one run, not one finding.** A finding retried across generations has one
thread per generation, and `workflow_state` deliberately collapses them to the newest
(`queries.py:190-197`) because it answers a per-finding question. The fleet answers a per-run one
and must not collapse.

**The repair record.** `GraphStore.migration_outcomes()` returns every attempt ever recorded
(`store.py:551-556`) with `terminal_status`, `strategy`, `tier`, `routing_row`,
`static_verify_passed`, `static_verify_error_class`, `ci_result`, `wall_ms` and the three token
counts (`src/sync/core/models.py:223-283` and following). Nothing in the tree exposes any of it —
there is no corpus route, no corpus view model, and no `features/corpus/` directory, though
slice 1's file structure named one.

**Repository identity, with a stated limit.** `repo_id` is a column on `call_site`
(`schema.sql:26`, `models.py:60`) and there is no `repository` table — `schema.sql` declares seven
tables and none of them is one. `sync.dashboard.queries` can see `repo_id` because it holds a
`GraphStore` (`queries.py:124`), but it emits none: `repository_overview` aggregates repositories
away into per-vendor counts and returns `{"vendors": [...], "indexed_at": ...}`
(`queries.py:119-137`). `store.call_site_counts(repo_id)` requires already knowing the id
(`store.py:431`).

So repository identity needs **one new `GraphStore` read** — `SELECT DISTINCT repo_id FROM
call_site`. `GraphStore` is internal, not frozen, and adding a read to it is allowed.

**Finding age.** `finding.created_at` is a column (`schema.sql:163`) and a model field
(`models.py:188`), read back by `open_findings`. It is invisible through `GraphSurface`, which
builds its rows from the call site and never the finding's timestamp (`tools.py:122-137`).

### Answerable only by changing the frozen surface — a question, not a task

**A repository on a `whats_at_risk` row.** `tools.py:122-137` builds each row from `site.path`,
`site.line`, `site.symbol`, `site.operation_id`, `site.vendor_id`, the change kind, the severity,
the finding id and the finding's rung. `site.repo_id` is available at that line and deliberately
not emitted. Scoping the *existing* hierarchy by repository therefore needs a field on a frozen
response. Asked as owner question 3; the fleet route does not need it, because it reads through a
view model instead.

### Not answerable by anything in the tree

- **A repository that was configured but never indexed.** There is no configuration table and no
  `RepoRef` is ever persisted — `RepoRef` (`models.py:56-63`) is constructed per run and lives in
  the checkpoint. The new `DISTINCT repo_id` read enumerates repositories the *index* knows, which
  makes "indexed, nothing open" distinguishable from "not in the graph at all" — but it cannot
  distinguish "not in the graph" from "never configured". **The screen must say which of those it
  is reporting.**
- **Whether a run is alive.** Decision 4 above. No heartbeat exists.
- **Closed findings.** `open_findings` filters `status = 'open'` and joins away retracted call
  sites (`store.py:495-518`). A "findings closed this week" figure has no source; `finding.status`
  is queryable but nothing reads it that way, and adding that read is a bigger question about what
  `patched` means when no PR merged.
- **Cost per run.** Tokens and `wall_ms` are on `migration_outcome`, whose grain is one attempt
  and which never receives a row for three abandonment classes at all — `corpus._record` returns
  early below `attempt_index` 1, so a run that abandoned before `patch` writes nothing (the
  run-state specification, *Standing constraints, checked*). A fleet cost figure computed from
  that table understates by exactly the runs that failed earliest. Report it as "cost of attempts
  that reached the patch node", or not at all.
- **Could not verify:** I did not execute a run or query a database in this worktree. Every claim
  about what a checkpoint holds mid-run is read from `queries.py:230-244`, from the langgraph
  source cited above, and from the fixtures in `tests/test_dashboard_queries.py:190-210`. The
  `checkpoint->>'ts'` field is documented in langgraph's `Checkpoint` TypedDict and appears in
  that fixture at line 196; I have not seen one written by a live run.

### The two deletions were overturned, and why that is not a reversal of the argument

Ruled 2026-08-05 by the controlling session and recorded in
`2026-08-05-sync-console-design-system.md` under question 3, which this note exists to point at
from the plan that would otherwise send an agent to delete six packages.

The owner asked for those capabilities directly, naming `@react-three/fiber`, `drei` and
`react-grid-layout` in a frontend scaffold specification, so a recommendation written before that
request cannot survive it. **What did not change is the argument.** Both rows reasoned about
whether to *build* the thing, and the design-system plan reaches the same conclusion on the merits
and by its own route: a spatial view is declined because occlusion makes "every affected call site
is shown" unprovable, and that claim is the only reason such a view would exist; a draggable
dashboard is declined because a fixed first version is what teaches a user what they want on
screen.

So the two plans never actually disagreed about what to build. They disagreed about what to
uninstall, and that is the smaller question. **Keeping a package for a condition that has not yet
been met is a different thing from declining the capability**, and conflating the two is what
produced a table row telling an agent to remove a dependency the owner had asked for.

The cost of carrying them is real and is accepted with its eyes open: six packages resolved on
every `npm ci`, none imported anywhere in `web/src`. `web/src/components/3d/README.md` carries the
decision where an agent reaching for the capability will actually look.

`echarts` and `echarts-for-react` stay installed and unused, and the distinction from the two
deletions is deliberate: those were rejected, this one is merely early. The corpus summary is the
first honest chart candidate in the product and it is one slice away.

## What I am not proposing, and what decided it

- **Prompt-injection defence for the patch agent.** The owner's own first recommendation and the
  research programme's best single finding — and it is days of work in `src/sync/remediate/`,
  needs a threat model before any code, and belongs to the session that owns that package. Putting
  it in a console slice would mean one reviewer holding two unrelated threat surfaces. It should
  be dispatched, just not here.
- **The abandonment vocabulary, either half.** The Python side is assigned to the `sync.remediate`
  session and gated on an owner ruling; the console side has nothing to render until it lands.
  Building the console half against a vocabulary that may be amended is a day spent twice.
- **A `repository` table.** `GraphStore.apply_schema` converges by issuing every column as `ADD
  COLUMN IF NOT EXISTS` and its docstring states it cannot rename, retype, constrain or backfill
  (`store.py:163-168`). A new entity table is a real migration, which is the framework that
  docstring argues against buying before it is needed. The `DISTINCT repo_id` read gets most of
  the value for an hour of work.
- **`repo_id` on the frozen `whats_at_risk` response.** Asked as a question instead. The cost is
  not the field, it is that a frozen surface changed once changes again.
- **A fleet health score, a traffic light, or a green liveness dot.** Rejected on the merits
  twice by the research and once by the run-state specification. A dot claims a fact the data does
  not carry (architectural decision 4).
- **Charts.** `echarts` is installed and the corpus summary would suit a bar chart. A table
  answers the same question, costs an afternoon less, and "functionality before polish" is a
  constraint this plan inherits rather than negotiates.
- **Server-sent events or a websocket in place of polling.** Polling was measured adequate — four
  polls in twenty seconds while live, none after terminal (`progress.md:141-143`) — and the
  critical path is a customer CI run measured in minutes. A push transport is a day and changes
  the deployment story for a latency nobody is waiting on.
- **Authentication.** There is no user model anywhere in the tree and the server binds 127.0.0.1
  by default (`__main__.py:35`). Auth is a slice with its own design, and pretending otherwise
  with a token check would be security theatre in the codebase whose whole claim is honesty.
- **A codename per finding** (`competitor-interfaces.md` §2.8). Cosmetic, unrelated to run state,
  and the finding id is already a stable hash a person can say aloud in eight characters.
- **A "findings closed this week" figure.** No source. See *Not answerable*.
- **Backfilling anything.** Two specifications and one model comment already argue that a guessed
  value and a measured one in the same column cannot be told apart afterwards.
